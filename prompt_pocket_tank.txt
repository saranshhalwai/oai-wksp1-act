3. GAME MODES AND COMPLETE RULES

Use score-based artillery. Tanks do not have health and are not eliminated by a hit. A hit scores points; destroying terrain changes the next shot's geometry. Do not accidentally turn this into a first-to-zero-health game.

Two presets:
- workshop-quick, the default: 5 shots per player, 20-second aiming deadline. Both players receive 2 Standard Shells, 1 Heavy Shell, 1 Scatter Volley, 1 Airburst Cluster.
- standard: 10 shots per player, 30-second aiming deadline. Both receive 3 Standard Shells, 2 Heavy Shells, 2 Scatter Volleys, 2 Airburst Clusters and 1 Borer Shell.

These are finite identical inventories for fairness and easy setup. No weapon draft in the required version. Both modes share the same backend/protocol. Select mode at room creation; freeze it once the second player joins.

Each round consists of one shot by each player. A server-generated coin toss selects the first player, who remains first each round. A rematch swaps sides and first-player priority. Wind changes once at the start of each round and is identical for both shots in that round. Clearly display wind direction and magnitude.

Turn sequence:
1. Server announces active player, turn ID, round, wind and aiming deadline.
2. Active player chooses angle, power and an available weapon, optionally uses one legal move, then fires.
3. Server validates and locks the shot, consumes exactly one ammunition item and calculates the outcome.
4. Both clients animate the same accepted shot timeline. All gameplay commands are locked during calculation/playback.
5. At the server-controlled end of playback, commit the final terrain, tank positions and score together, then open the next turn.
6. After both players use all allotted shots, highest total score wins. Equal scores produce a draw. Misses still consume shots/ammunition.

Aim controls:
- Global world angle: 0 degrees points right, 90 up, 180 left. Use integer degrees, inclusive range 0–180.
- Power: integer 1–100. Canonical launch speed is 100 + 4*power world units/second.
- Initial left-tank angle 45, right-tank angle 135, initial power 60. Retain each player's last accepted settings across their turns when valid; choose the first remaining weapon if the old selection is exhausted.
- Slider, numeric controls, keyboard and pointer aiming must map to the same canonical angle/power values.
- Basic preview is the barrel direction and a short fixed-length direction guide, independent of power. No full trajectory, landing marker, recommended settings or automated targeting in competitive mode. The client SDK must not expose a calculate-best-shot function.
- This assistance restriction is a workshop rule, not cryptographic anti-cheat: public terrain/physics can be reverse-engineered. Server authority prevents forged outcomes, but cannot prove that a custom frontend has no aiming aid. Explain this in the host guide and use review/judging for compliance.

Optional movement within the required rules:
- Each player starts with 3 move tokens in quick mode or 6 in standard mode.
- At most one move per turn, before firing. A move requests left/right, for up to 24 world units, never arbitrary coordinates.
- Walk along terrain support in small swept increments; require at most 6 units of step-up and 12 units of step-down per increment, no hull penetration and no tank overlap or side-bound crossing.
- Move the furthest legal distance; if zero, reject without consuming a token. Otherwise consume one token and mark the turn's move used.
- Return accepted path/final position; animate it briefly. Fire is disabled until the server-controlled move phase finishes. The turn deadline continues running. If it expires during movement, complete the accepted move then perform the timeout action once.
- Terrain collapse after explosions is a separate settling operation and can drop tanks farther than voluntary movement permits.

Timeout: use the last server-confirmed aim/weapon, or the defaults if none, to fire automatically. Display this policy. A fire packet received at or after the server deadline loses to the timeout action; duplicate/racing commands must never create a second shot. The deadline uses server receive time, not an untrusted client timestamp.

4. WORLD, TERRAIN AND TANK GEOMETRY

World coordinates: 1024 units wide by 576 units high; origin top left; x right, y down. Fixed logical size independent of canvas/device resolution. Sky/background artwork has no collision.

Terrain is a canonical 1024x576 one-bit occupancy mask: empty or solid, 1 world unit per cell, approximately 72 KiB when bit-packed. Use a typed bitset or a byte array internally if simpler, but use compact binary transport for full snapshots. Do not derive collision from the frontend's colored pixels or use different collision scales in different themes.

Generate smooth seeded terrain with a continuous ground surface, no overhangs initially, ground heights roughly y=300..440. Flatten two initial support areas around x=140 and x=884. Keep spawn support height equal and use left-right symmetric initial terrain. Keep an indestructible 8-unit bedrock strip along the bottom. Seed and terrain version are server-owned.

Use real mask subtraction for circular craters and drill cuts, including holes/overhangs. Terrain itself is static after removal: no expensive sand or floating-island collapse simulation. Visually make this behavior consistent. Tanks settle under gravity after all weapon impacts in a shot have resolved. Do not silently replace the mask with a heightfield that fills tunnels.

Tank geometry: a canonical axis-aligned hull 28x16 units, barrel pivot derived from hull center/top by a shared transform, barrel length 20 units. Hull collider stays axis-aligned for this version; cosmetic suspension/tilt cannot change collision or muzzle origin. Provide exact hull/pivot/muzzle helpers in the SDK.

Spawn and settling:
- Tanks occupy clear space above supporting terrain. Falling performs swept hull collision against solid cells/bedrock and stops at first support; never teleport through a ledge or tunnel floor.
- If initial hull placement overlaps terrain, fix generation rather than silently tolerating it.
- No fall damage, crushing, tank death or burial/filling weapons in the required version.
- Keep tanks within their side ranges: left center x=32..480, right center x=544..992. Voluntary movement cannot swap sides or cause overlap.
- After final terrain edits, settle tanks downward using the same deterministic algorithm and include the settling animation in the shot timeline. Clamp work and assert no hull/terrain overlap or missing support in the committed result.

For each committed state include terrainVersion and a stable checksum. Send a full terrain snapshot on first join/reconnect or mismatch; use versioned row-span patches between turns. Patches explicitly carry baseVersion, newVersion, bounds and checksum. Reject/request resync on gaps, invalid bounds or mismatch. Packet assembly must be bounded; never assume a text JSON array per cell is acceptable transport.

5. PHYSICS, COLLISION AND WEAPONS

Only the server calculates official impacts, scores and terrain edits. Clients render accepted samples/events. Never accept client-provided hit coordinates, damage, final tank positions, terrain patches or score.

Projectile physics:
- Fixed step dt=1/120 second; choose and document one integration method and stable update order.
- Gravity 180 world units/second squared, downward. Wind is horizontal acceleration uniformly selected as an integer in [-25,25] for each round.
- Launch from the shared muzzle origin using vx=speed*cos(angle), vy=-speed*sin(angle). Recompute muzzle from committed tank position and accepted angle.
- Projectile collision radius 2 units. Sweep from previous to new position against the mask and tank hulls to prevent tunneling. Resolve earliest time of contact, with an explicit deterministic tie-break.
- Ignore the firing tank only until the projectile has fully exited its hull/muzzle area; a later return can hit its owner. Handle muzzle blocked by terrain immediately and consistently.
- x<0 or x>=1024 ends that projectile as a miss. Allow y<0 flight with an offscreen indicator; do not destroy at the top edge. Bound simulation at 12 seconds per shot and y<-2048; expire remaining projectiles without inventing an impact.
- Use one seeded PRNG stream per shot where randomness is needed. Stable entity IDs/order and terrain edit order make runs repeatable on the server. Do not depend on bit-identical browser floating-point simulation for synchronization.

Baseline weapon definitions (all metadata shared with clients):
- Standard Shell: one projectile; explosion radius 36; max score contribution 40; terrain removal radius 30.
- Heavy Shell: one projectile; explosion radius 54; max contribution 65; terrain removal radius 48. Same launch-speed formula for predictable power controls.
- Scatter Volley: three projectiles launched simultaneously at angle offsets -6, 0, +6 degrees, clamped to [0,180]; each explosion radius 24, max contribution 18, crater radius 20. One ammunition use. Fixed stable ordering for same-step impacts.
- Airburst Cluster: main projectile bursts once at the first apex crossing, before terrain contact if it reaches an apex. Spawn five children with fixed horizontal velocity offsets [-90,-45,0,45,90] added to parent vx and downward vy=40. Each child: explosion radius 22, max contribution 16, crater radius 18. If the main hits first, explode once with radius 24/max 20/crater 20 instead. No recursive splitting; at most five live children.
- Borer Shell: on first terrain contact, cut a radius-6 corridor along the incoming direction for up to 60 units then explode with radius 34/max 35/crater 30. It stops at first tank contact, bedrock or world boundary. A direct tank contact before terrain detonates immediately. Drill progress is deterministic and represented as timed terrain edits; do not teleport an explosion past a tank.

Keep these as original workshop weapons; do not reproduce a commercial game's weapon catalogue, names/art/audio or undocumented balance. Use a weapon-handler registry, with explicit bounded phases for flight, split/drill, impact and finish. No arbitrary runtime scripts supplied by clients.

Scoring:
- For each explosion and each tank, compute distance d from explosion center to the nearest point of the hull AABB at that moment.
- contribution = round(maxScore * max(0, 1-d/explosionRadius)). Exact radius edge gives zero.
- Add contributions against the opponent to the shooter; subtract contributions against the shooter from the shooter's score. Negative totals are allowed. The non-shooter's score does not change from being hit.
- No separate direct-hit bonus; d=0 already gives maximum. No terrain shielding for explosion scoring in this version; surface/tank collision still controls where projectiles stop.
- Sum all unique explosions in a shot, including multiple scatter/cluster hits. Explosion IDs ensure each contribution applies once.
- Tanks remain stationary during projectile/impact resolution and settle only after all explosions and drill edits in the shot. This makes multi-impact scoring unambiguous.
- Score events must show opponent points and self-penalty separately, plus net shot score. Do not present them as health damage.

6. SERVER AUTHORITY AND SHOT TIMELINE

Use a room state machine: waiting, countdown, aiming, moving, calculating, playback, finished, aborted. Transport connection state is separate. Both players ready triggers a 3-second countdown. Third-player joins are rejected; no mid-match replacement seat. Use random unambiguous six-character room codes with collision checks and expiration.

During fire processing:
1. Authenticate session/seat; check match ID, turn ID, phase, deadline, command ID, ammo, angle and power.
2. Atomically mark that turn as fired, record the accepted command and reserve/debit one ammo. No other input can change this shot.
3. Submit an immutable terrain/tank/config snapshot to a bounded worker pool. Inputs determine the shot; no client physics is used.
4. Receive a bounded result containing sampled projectile tracks, ordered impact/split/drill/score/settle events, terrain edits, final checksum, final positions and score delta.
5. Schedule playback with a server start timestamp about 150 ms ahead, then publish the accepted timeline. Packet preparation is off the hot path; chunk large data with IDs and bounded sizes if needed.
6. Commit authoritative final state exactly once at playback end, then start the next turn. A browser's “animation complete” must never advance the room. Include enough data for late clients to fast-forward/resync.

The state while playing an animation is not the same as the final committed next-turn state. Define this explicitly: authoritative committed state plus in-flight shot timeline, and a derived SDK render state at playback time. Apply each visual terrain edit at its impact time; do not reveal the complete crater at projectile launch. Transient score popups can follow events while committed totals advance at the defined boundary.

Transmit server-computed trajectory samples at about 30 samples/second, including exact impact/split points and timestamps. Clients interpolate those for smooth 60 FPS animation; impacts use exact event positions, not an interpolated guessed collision. Logical physics continues at 120 Hz inside shot calculation. Rendering refresh rate, client speed and network broadcast rate do not determine physics.

Bound worker job duration, active projectiles, simulation steps, events, queue length and payload size. On worker error/timeout, keep state consistent: abort the match with an explicit server error and no winner; never partially commit terrain or award a winner. Ignore late job results for a stale match/turn or aborted room. Catch and report failures; do not allow jobs to accumulate forever. Target p95 accepted-shot calculation under 100 ms on the tested deployment; report actual performance instead of claiming the target was reached.

7. COMMANDS, STATE AND NETWORK RECOVERY

Every mutating command includes protocol version, match/turn identity when applicable and a unique command ID. Provide authoritative ack/reject responses. Cache bounded command outcomes so retrying an accepted fire/move is idempotent. A conflicting payload with the same command ID is rejected. Old-turn requests cannot affect a new turn or rematch. Resolve session identity from the authenticated connection, not a client-supplied player ID.

Public commands: create/join room, ready, setAim, selectWeapon, move left/right, fire, requestRematch, leave and resync. Merge aim and weapon draft changes in one versioned command if it simplifies ordering. A fire command must carry its final angle, power and weapon explicitly so it cannot race a throttled aim update.

Public state: protocol/rules/physics versions, build ID, room/match/turn IDs, mode, phase, player IDs and slots, tank geometry/positions, inventories, scores, move tokens, active player, round, wind, aim deadline, accepted aim state, terrain version/checksum and current playback reference.

Use event-driven WebSockets/WSS. HTTP may serve initial room lookup/bootstrap and static assets, never poll game state. Aim controls update immediately in the local UI; coalesce remote aim updates to at most 10 Hz. There is no need to send 60 network messages/second merely because a slider is animated at 60 FPS.

When Fire is pressed, immediately show pending feedback and disable duplicate fire; start the official projectile only after acceptance/timeline availability. Do not fake a hit or alter terrain before server acceptance. Record input-to-ack and ack-to-animation separately.

Clock/playback:
- Estimate server time using a ping/echo exchange with monotonic local elapsed time; track uncertainty/smoothing. Do not assume matching wall clocks.
- If a timeline arrives after its start time, seek to current playback time and apply missed terrain/event state without replaying old sounds.
- On disconnect/tab suspension, resync snapshot, active timeline, playback time and committed terrain version. Discard stale drafts/pending effects; do not replay old commands automatically across turns.
- Retain a bounded active/recent timeline until its recovery window ends. Reconstruct render state from a versioned base plus ordered edits, or send a current materialized snapshot with the correct playback cursor. Test this path in the middle of a cluster/drill shot.
- If a client cannot assemble/validate a timeline, show synchronizing and obtain a snapshot. Never continue drawing guessed terrain.

Reconnect policy:
- Keep a temporary seat for 20 seconds using an unguessable reconnect credential, including support for same-tab refresh through SDK session storage.
- Gameplay/playback and deadlines continue; an absent active player can time out into the defined automatic shot.
- If one remains absent at grace expiry, forfeit to the connected player unless a final result already exists. If a shot is in progress, mark the pending terminal reason and finish that accepted shot before finalizing; do not open another turn.
- If both remain absent beyond their grace periods, abort with no winner. An explicit leave triggers the same terminal policy immediately. Later timers/jobs cannot overwrite the result.
- A transient reconnect before grace expiry clears that disconnect's pending forfeit. Distinguish it from an explicit leave. Specify/test races at grace and playback boundaries.
- Server restart ends in-memory rooms. Do not claim session recovery across server restarts.

Measure real application RTT p50/p95, a defined jitter/variability statistic, command acknowledgment delay, shot calculation time, playback skew estimate, resync count and client FPS. A 20–60 ms median RTT remains a desirable venue target, not a guaranteed requirement for game correctness. Verify usability at 150 and 300 ms RTT too: local aim stays immediate; firing acknowledgment waits longer, while the accepted animation remains smooth. Do not claim measured one-way latency by halving RTT.

Validate finite values, bounded strings/messages, angle/power ranges, available weapon IDs and legal phases. Limit room creation and per-session command rates; allow aggregate campus traffic behind one public IP. Browser Origin checks supplement player/session validation; they are not authentication. Never log reconnect credentials or expose administrative secrets in frontend configuration.

13. GOOGLE CLOUD DEPLOYMENT AND OPERATION

13.1 Architecture and service choice

Deploy one standard (non-Spot) Google Compute Engine VM running Docker Compose. Run exactly one authoritative Node/Colyseus game process, its bounded worker-thread pool, and a Caddy container that serves both built frontend bundles and reverse-proxies HTTP/WebSocket backend traffic. Store private application images in a regional Artifact Registry repository. Use Google Cloud Logging and Monitoring through an explicitly configured Ops Agent on the VM.

Choose Compute Engine because room state is held in one process's memory. Cloud Run supports WebSockets, but requests have configured timeouts and session affinity is best-effort across connections. Autoscaling would require explicit authoritative room placement/shared coordination; a room code and sticky-session setting alone do not solve it. Do not implement Cloud Run, Cloud Functions, GKE, a managed instance group, Redis or a database for this baseline. Do not claim Cloud Run cannot run WebSockets. Scaling beyond this single process is future work, not an unimplemented promise in the handoff.

Use one stable public origin, for example https://GAME_DOMAIN, with /neon/ and /paper/ for the sample clients. Use the actual compatible Colyseus HTTP/matchmaking and WebSocket routes; write and test the proxy configuration against them instead of assuming a guessed /ws path. A friendly landing page at / links both examples and the participant download. Participants can run localhost frontends or separately hosted frontends connecting directly to the same secure backend origin.

Frontend build output is included in the web image. No separate Firebase Hosting, Cloud Storage website, CDN or external load balancer is required. These can be documented as future alternatives, but must not complicate the required setup.
